# 📄 ADR-001: MDX Driven Content Architecture

## Status

Accepted

## Date

2026-02-08

---

## Context

The portfolio website requires:

* Scalable content authoring
* Rich storytelling capability
* UI component reuse for OSS library
* Strong TypeScript safety
* Consistent visual design system
* Ability to auto-generate sections from content files

Traditional approaches considered:

1. Hardcoded TSX content
2. CMS driven content
3. MDX free-form content
4. Structured MDX with controlled components

---

## Decision

The project will use:

### ✅ MDX as content source with controlled component injection

---

MDX files will:

* Export structured metadata
* Contain markdown prose
* Use only whitelisted UI components
* Not control layout or page structure

---

## Architectural Principles

### 1. Layout Ownership

Layout must be controlled by TSX controllers and UI components.

MDX is strictly presentation-content layer.

---

### 2. Controlled Component Exposure

MDX components must be provided via:

```
MDXProvider component registry
```

Direct imports inside MDX are forbidden.

---

### 3. Strong Type Safety

MDX modules must conform to:

```
MDXModule<TMetadata>
```

Content loaders enforce schema typing.

---

### 4. File-Based Content Discovery

Content is automatically discovered using:

```
import.meta.glob()
```

---

## Implementation Structure

```
content/
   timeline/
   projects/
   expertise/

types/
   mdx.ts
   <content-type>.ts

controllers/
   loadTimeline.ts

mdx/
   components.ts
   wrapper.ts

ui/
   mdx/
   timeline/
```

---

## Consequences

### Positive

* Strong compile-time safety
* Scalable content authoring
* Portable UI components
* Supports OSS UI library extraction
* Allows storytelling flexibility
* Enables static site generation compatibility

---

### Negative

* Requires metadata schema discipline
* Requires strict MDX authoring rules
* Slightly increased loader complexity

---

## Rejected Alternatives

### ❌ Free-form MDX Layout Control

Rejected due to styling inconsistency and UI library extraction difficulty.

---

### ❌ CMS Backend

Rejected due to unnecessary complexity for portfolio scale and developer ownership preference.

---

### ❌ Pure TSX Content

Rejected due to poor authoring scalability and duplication risk.

# 📄 ADR-003: Metadata Export Convention

## Status

Accepted

---

## Decision

All MDX files must export:

```
export const metadata
```

---

## Rationale

* Enables generic loader design
* Avoids naming ambiguity
* Supports strict TypeScript generics

---

## Forbidden Variants

```
meta
data
info
frontmatter
```

# 📄 ADR-004: Multi-Repository Architecture Strategy

## Status

Accepted

## Date

2026-02-08

---

## Context

The portfolio ecosystem is expected to grow beyond a single website. Planned deliverables include:

* Portfolio website
* Independent project websites
* OSS UI component library
* Shared content and tooling utilities
* Static multi-site deployment pipeline

Maintaining all concerns in a monorepo was considered but rejected due to:

* OSS release complexity
* Independent project lifecycle needs
* Desire for clear separation of concerns
* Easier public contribution flows

---

## Decision

The platform will use a **multi-repository architecture** coordinated via Git subtree integration and unified static deployment.

---

## Repository Responsibilities

### 🧩 1. Portfolio Repository (Aggregator + Host)

Primary responsibility:

```
Central static site entry point
```

Contains:

* Portfolio homepage
* Content engine
* Navigation and routing
* Aggregation of sub-project sites
* CI/CD orchestration
* MDX content source

---

### 🧩 2. UI Library Repository (OSS)

Primary responsibility:

```
Reusable design system components
```

Contains:

* Layout primitives
* Content display components
* MDX-compatible content components
* Design tokens
* CSS Modules styling system

---

### 🧩 3. Individual Project Repositories

Primary responsibility:

```
Project code + project website
```

Each project repo contains:

* Application source code
* Project-specific website
* Documentation
* Independent versioning

---

---

# 📄 ADR-005: Subtree-Based Website Integration

## Status

Accepted

---

## Decision

Project websites will be integrated into the portfolio using:

```
Git Subtree
```

---

## Rationale

Subtree allows:

* Independent project repositories
* Direct embedding of website source
* Version synchronization without monorepo complexity
* Easier OSS contribution boundaries

---

## Subtree Strategy

Each project repo will maintain:

```
portfolio branch
```

Containing only:

```
Website source
```

Portfolio repo pulls subtree from that branch.
